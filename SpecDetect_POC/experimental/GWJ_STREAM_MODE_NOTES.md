## 一、stream 传输方式是国标规定

### 原文摘录

> (p509) 服务提供者告诉服务消费者采用异步传输的方式，对于数据流采用 **stream 方式**传输，对于其他形式结果采用**轮询**的方式获知结果数据是否已经给出。

> (p842) 设备端成功响应，对请求测量参数给予确认，并声明在 **172.18.225.78 主机上的 5000 端口使用 stream 的方式**可以获得宽带 FFT 频谱数据。

> (p1007, p3104) 类似表述，应用于扫频频谱、扫频截收等服务。

### 含义

- **SOAP 控制面**: 客户端发请求 → 设备/Atom 响应里带 `host:port + stream`
- **数据面**: 客户端按该 host:port 建 TCP 连接，收 GWJ004 帧流
- **streamsrc 18012 即是这种 stream 通道**，只是 Atom 额外做了私有压缩

这回答了之前 `DATA_FLOW_END_TO_END.md` 段 3 标"未验证"的"SOAP 数据面实际传输通道"问题：
> SOAP 控制 + stream 数据双通道 = **国标标准形态**。

## 二、频谱数据单位精度差异

### 两种单位并存

| 文档 | 字段 | 单位 | 精度 |
|---|---|---|---|
| GWJ006 §5.2.1 表10 | 电平 INT16 | `0.1 dBμV` | 0.1 |
| 工信部2016379号 t38r5/t39r6 | 频谱数据 INT16 | **`0.01 dBμV`** | 0.01 |

### 含义

- 不同规范/不同业务里，INT16 电平的单位因子不同（×10 或 ×100）
- 解析 streamsrc/rmcp 原始值 → dBm 时必须先确认适用的单位因子
- 当前 streamsrc 值范围 `[-32768, 24933]`，若按 `0.01 dBμV` 解释：
  - 24933 × 0.01 = 249.33 dBμV → 减 107.6 = 141.7 dBm （显然不对）
  - 按 `0.1 dBμV`: 2493.3 dBμV → 不对
  - 所以 streamsrc 值 **不是直接的 0.1/0.01 dBμV 定点**，需要额外归一化

这支持"Atom streamsrc 是私有归一化格式"的结论。

## 三、异步传输模型

**控制/数据分离**（p509 明确）：

```
┌────────┐  SOAP 请求 (同步)     ┌──────┐
│ Client │ ───────────────────► │ Atom │
│        │ ◄─────────────────── │      │
│        │  SOAP 响应: host:port + stream
│        │                       │      │
│        │  stream TCP (数据流)  │      │
│        │ ◄═══════════════════  │      │
│        │                       │      │
│        │  轮询请求 (其他结果)  │      │
│        │ ───────────────────► │      │
└────────┘                      └──────┘
```

**印证 Atom 分叉输出**:
- 控制面 → SOAP
- 数据面 → stream (即 streamsrc 18012)

## 五、仍未回答的问题

以下 Atom 私有行为在所有国标文档中均**未涉及**：

1. 量化算法（848 级 → 16 级）
2. 底噪压平策略（-62.8 dBm 钉住）
3. 529/434 的频段选取逻辑
4. streamsrc 65 字节帧内部 offset 19/20 等私有字段
5. `[-32768, 24933]` 归一化公式

这些仍需通过 Atom 二进制逆向或动态跟踪解决。
