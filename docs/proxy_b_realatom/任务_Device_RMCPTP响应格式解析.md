### 观察到的现象

**rmcp_proxy 捕获的 DATA 帧** (`capture_20260411_141437.log`):

| 时间 | 帧类型 | 大小 | 说明 |
|------|--------|------|------|
| 14:23:46.500 | S->C DATA | 1053 bytes | Device -> Atom |
| 14:23:46.610 | S->C DATA | 1053 bytes | Device -> Atom |
| 14:23:46.751 | S->C DATA | 863 bytes | Device -> Atom |

**SCPI 客户端日志显示**:

```
总的数据长度1062
解析原子数据帧头：
LEADER:-286331154 VER:1 STC:1775888625 TS:2026-4-11 14:23:47:485 PL:1062 EL:0
解析原子数据帧体:
扫频频谱观测数据:DT:12 DL:1057
频段序号:1  信道总数:1441
起始频率:137.0000MHz  结束频率:149.7750MHz
步长:25.0000kHz  帧信道数量:512
电平: -66  -65  -82  -71 ...
```

### 关键发现

1. **rmcp_proxy 捕获的数据与 SCPI 显示的数据格式不同**
2. SCPI 日志中有 `LEADER=-286331154`, `DT=12` 等标记
3. rmcp_proxy 捕获的 DATA 帧 DT 值为 253, 118, 110 等，不是 12

### 结论

- **rmcp_proxy** 捕获的是 Device 发回的**原始 RMCPTP 响应**
- **SCPI 日志**显示的是 Real Atom **解析处理后**的数据
- Real Atom 在接收 Device 数据后，会进行格式转换再通过 streamsrc 转发

## 分析步骤

### 步骤1: 对比 rmcp_proxy 和 SCPI 日志的时间戳

从 `capture_20260411_141437.log` 分析：

```
14:23:46.500  S->C DATA (1053 bytes)  ← rmcp_proxy 捕获
14:23:47.485  PL:1062, DT:12         ← SCPI 显示
                        ↑
                   时间差约 1 秒，可能是 Atom 处理延迟
```

### 步骤2: 分析 Device 原始响应格式

**捕获数据分析**:
- Frame #2: 1053 bytes, DT=152 (第一帧)
- Frame #3: 863 bytes, DT=23
- 帧间隔约 100ms

**原始数据特征**:
```
First 60 bytes (hex):
0F 01 00 00 02 00 00 00 00 00 00 FA FC 85 FD 59 FD 3E FD 92
FD 75 FD 98 FD 5C FD E3 FD 6E FD DA FD 10 FD D2 FC 25 FD B0
```

### 步骤3: 查找 Device RMCPTP 协议规范

可能的数据格式选项：
1. **自定义二进制格式** - Device 返回的测量原始数据
2. **编码后的频谱数据** - 需要解码才能看到频谱值
3. **压缩格式** - 数据被压缩过

### RMCPTP 帧格式

```
RMCPTP 帧头 (18 bytes):
+--------+--------+--------+--------+
| dwLength (4) | tmStamp (8)       |
+--------+--------+--------+--------+
| nVersion (2) | nMsgType | nFlags |
+--------+--------+--------+--------+
| nCheckSum (2)                    |
+--------+--------+--------+--------+
```

### 已知的消息类型

| nMsgType | 名称 | 说明 |
|----------|------|------|
| 90 | REQUEST | SOAP 请求 |
| 6 | RESPONSE | 命令响应 |
| 0 | DATA | 业务数据 (Device 持续回传) |
