## 2. 服务调用流程（4 步）

```
Step 1: 监测设施/设备列表查询 (11.2.7)
  → 通过行政区编号获得设备清单

Step 2: 监测设备详细信息查询 (11.2.8, QueryDeviceInfo)
  → 获得设备基本信息和原子服务能力列表

Step 3: 监测设备状态信息查询 (11.1.24, QueryFacilityDevStatus)
  → 查询设备当前状态（idle/busy），决定是否可发起服务请求

Step 4: 请求服务
  → 向设备发起测量服务请求
```

## 3. 设备状态查询接口定义

### 3.1 SelfTest（监测设备自检）— §11.1.23

**用途**：检查设备是否正常可用（可在发起测量前调用）。

**请求**：
```xml
<query type='get'>
  <mfid val='监测设施 ID'/>
  <equid val='监测设备 ID'/>
  <resulttype></resulttype>
</query>
```

**成功响应**：
```xml
<query type='result'>
  <mfid val='监测设施 ID'/>
  <equid val='监测设备 ID'/>
  <available/>
</query>
```

> 设备端成功响应，并声明监测设备是正常可用的。

**说明**：`<available/>` 元素表示设备可达和正常。这是规范中用于判断设备是否可用的最基本机制。

### 3.2 QueryFacilityDevStatus（监测站/设备状态查询）— §11.1.24

**用途**：获取设备的当前位置、运行状态、正在执行的任务等信息。

**输入参数**：
| 参数 | 说明 |
|------|------|
| mfid | 监测设施 ID |
| equid | 监测设备 ID（可选，不给则返回该设施所有设备状态） |

**输出参数**：
| 参数 | 说明 |
|------|------|
| position | 位置信息（经度、纬度、海拔高度） |
| state | 前端监测设备的运行状况（idle/busy） |
| task | 正在执行的功能任务、任务 ID |
| speed | 移动速度（移动站） |
| direction | 移动方向 |
| compass | 电子罗盘方向 |

**请求**：
```xml
<query type='get'>
  <mfid val='监测设施 ID'/>
  <equid val='监测设备 ID'/>
</query>
```

**成功响应**：
```xml
<query type='result' xmlns='base'>
  <mfid val='监测设施 ID'/>
  <position longitude='经度' latitude='纬度' ltitude='海拔高度'>
    <speed val='速度'/>
    <direction val='方位'/>
    <compass val='方位'/>
    <equid val='监测设备ID'>
      <state val='运行状态'/>
      <task val='监测功能代码'>任务ID</task>
    </equid>
  </position>
</query>
```

**范例（一台 idle，一台 busy）**：
```xml
<query type='result' xmlns='base'>
  <mfid val='21130001110001'/>
  <position longitude='120.44996' latitude='41.574767' ltitude='170'>
    <equid val='39A34F83A463278E23JG6EB87BVE5FTR3EEA'>
      <state val='idle'/>
    </equid>
    <equid val='89AEBF83A46F878E2389AEB879AE5F893EBX'>
      <state val='busy'/>
      <task val='FScan'>task_id</task>
    </equid>
  </position>
</query>
```

> 设备端成功响应，此监测站的两台设备一台空闲，一台正在执行扫描频谱观测（FScan），任务 ID 是 task_id。由于是固定站设备，没有移动速度、移动方向及罗盘方位信息。

**错误响应**：
```xml
<query type='error'>
  <error type='type'>
    <code/>
    <text>详细的错误描述</text>
  </error>
</query>
```

### 3.3 QueryDeviceInfo 中的 equstatus — §11.2.8

QueryDeviceInfo 返回静态的 `equstatus`（设备状态编码）字段，与 QueryFacilityDevStatus 的运行时 state 不同：

```xml
<equstatus val='设备状态编码'/>
```

实测值为 `01`。这是数据库级状态码（如 01=在线，02=离线），定义于《超短波频段监测管理数据库结构技术规范（试行）》。

## 4. 关键发现

### 4.1 无 RMCP 级状态查询

在整份 119,473 字符的规范文档中，以下术语 **零匹配**：

| 搜索词 | 结果 |
|--------|:--:|
| 心跳 (heartbeat) | 无 |
| keep-alive | 无 |
| 连接状态 | 无 |
| 在线/离线（作为协议术语） | 无 |
| RMCP 状态查询 nBdType | 无 |

**RMCP 协议（RX-RMCPTP）是纯测量数据传输协议**。设备状态查询完全是 SOAP 服务层面的概念。

### 4.2 无心跳/保活机制

规范没有定义任何心跳、keep-alive 或设备上下线通知机制。平台必须通过以下方式主动判断设备状态：
1. SelfTest → `<available/>`（基本可达性）
2. QueryFacilityDevStatus → state=idle/busy（运行时状态）
3. TCP 连接状态（本地快速判断，但不可单独依赖）

### 4.3 工信部规范与 GWJ003 差异

| 字段 | 工信部无2016379号-1 | GWJ003-2015 |
|------|---------------------|-------------|
| QueryFacilityDevStatus `<task>` 内容 | **任务ID** | **任务下达人（user_id）** |
| 其它 | 基本一致 | 基本一致 |

## 6. 对实现的影响

### 6.1 当前实现策略正确

B_QueryFaciDevStat 基于本地 SessionManager 状态——这**符合所有规范文档的设计意图**。规范定义的是 SOAP 层面的服务，不涉及 RMCP 硬件查询。

### 6.2 无需实现 RMCP 级状态查询

- 规范未定义 RMCP 状态查询命令
- 实现它将成为非标准扩展，与其他规范实现不兼容
- SelfTest 是规范定义的"可达性检查"机制，可用于测量前验证

### 6.3 可选增强

1. **SelfTest 实现**：添加 `<available/>` 检查，作为测量前设备可达性验证
2. **position 字段**：当前硬编码 altitude=0.0，未实现 longitude/latitude/speed/direction/compass
3. **多头设备支持**：规范支持一个 mfid 下多个 equid 的状态返回，当前实现为单设备
